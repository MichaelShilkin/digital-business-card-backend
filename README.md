# Digital Business Card — Backend

Backend цифровой визитки: профиль, навыки, опыт работы и проекты. Данные отдаёт GraphQL API, посмотреть и выполнить запросы можно в Apollo Sandbox.

- **Работающий проект (Apollo Sandbox):** https://digital-business-card-backend-production-e33f.up.railway.app/graphql
- **Исходный код:** https://github.com/MichaelShilkin/digital-business-card-backend

Запрос для проверки (вставьте в Sandbox и нажмите Run) есть в разделе «Примеры запросов».

## Технологии

| Технология | Зачем |
|---|---|
| **TypeScript** | типизация от схемы БД до GraphQL |
| **Node.js 24** | среда выполнения |
| **NestJS 12** | модули, внедрение зависимостей, разделение слоёв |
| **GraphQL (Apollo Server)** | API, подход code-first |
| **Prisma 7** | типобезопасный доступ к БД, миграции |
| **PostgreSQL 16** | реляционная база данных |
| **Docker / Docker Compose** | запуск приложения и базы одной командой |
| **Git** | история изменений |

## Быстрый старт

### Вариант 1. Docker (ничего не нужно устанавливать, кроме Docker)

```bash
docker compose up --build
```

Поднимутся PostgreSQL и приложение. При старте приложение само применит миграции и заполнит пустую базу данными. Порт 3005 должен быть свободен.

### Вариант 2. Локально

Нужны **Node.js 24.9+** (см. `.nvmrc`) и запущенный Docker (для PostgreSQL).

```bash
npm install
cp .env.example .env     # на Windows: copy .env.example .env
npm run start:dev
```

`npm run start:dev` сам выполнит всё необходимое:

1. Запустит PostgreSQL через Docker Compose и дождётся его готовности.
2. Сгенерирует Prisma Client.
3. Применит миграции.
4. Заполнит базу данными, если она пуста.
5. Запустит NestJS в режиме разработки.

### Apollo Sandbox

После запуска откройте **http://localhost:3005/graphql**. Адрес также выводится в консоль при старте.

## Примеры запросов

Запрос без аргументов возвращает профиль визитки:

```graphql
query {
  profile {
    name
    description
    skills {
      name
    }
    experience {
      company
      position
    }
    projects {
      name
    }
  }
}
```

Полный набор полей, включая период работы и достижения:

```graphql
query {
  profile {
    id
    name
    title
    description
    email
    githubUrl
    linkedinUrl
    skills {
      id
      name
    }
    experience {
      id
      company
      position
      startDate
      endDate
      achievements
    }
    projects {
      id
      name
      description
      url
    }
  }
}
```

Необязательный аргумент `id` выбирает конкретный профиль: `profile(id: 1)`. Если профиля с таким `id` нет, вернётся `null`.

## Архитектурные решения

### Слои приложения

```text
GraphQL (AppResolver)  →  бизнес-логика (ProfileService)  →  доступ к данным (PrismaService)  →  PostgreSQL
```

- **`AppResolver`** описывает GraphQL API и ничего не знает о базе данных. Он принимает запрос и передаёт его сервису.
- **`ProfileService`** содержит логику получения профиля: выбор профиля, обработка ошибок, логирование.
- **`PrismaService`** единственное место, где создаётся подключение к БД. Все остальные слои получают его через внедрение зависимостей.
- **GraphQL-модели** (`*.model.ts`) описывают формат ответа API отдельно от модели БД. Схема API может меняться независимо от таблиц.

Такое разделение позволяет тестировать сервис без базы (Prisma подменяется заглушкой) и менять один слой, не затрагивая остальные.

### Модель данных

Основная сущность `Profile`. С ней связаны `Skill`, `Experience` и `Project` связью один ко многим. Профиль описывает визитку, а навыки, места работы и проекты принадлежат ему и не имеют смысла отдельно, поэтому при удалении профиля они удаляются каскадно (`onDelete: Cascade`, на уровне внешних ключей БД).

Период работы хранится двумя датами: `startDate` и необязательной `endDate` (текущее место работы не имеет даты окончания).

### Вложенные данные

Профиль со всеми связями загружается **одним вызовом Prisma Client** через `include`. Это исключает проблему N+1, когда на каждый навык, место работы или проект выполнялся бы отдельный запрос. Резолверы вложенных полей не нужны: данные уже приходят вместе с профилем.

Компромисс: связи загружаются всегда, даже если клиент запросил только `name`. Для визитки с десятком записей это несущественно. При росте данных следующий шаг: читать из GraphQL-запроса, какие связи нужны, и подключать только их.

### Аргумент `id` необязателен

Запрос без аргументов возвращает первый профиль: приложение это одна визитка, и клиенту не нужно знать идентификатор. Аргумент `id` оставлен для случая нескольких профилей.

### Подготовка и заполнение базы

Структура и данные разделены:

- **Структура БД** меняется только миграциями Prisma (`prisma/migrations/`). Они применяются при каждом запуске (`prisma migrate deploy`) и безопасны для повторного выполнения.
- **Данные визитки** лежат в `prisma/seed-data.ts`. Seed при запуске заполняет базу **только если она пуста**. Существующие данные он никогда не перезаписывает: перезапуск приложения не должен менять то, с чем уже работают.
- **Восстановить эталонные данные** можно только явной командой `npm run db:reseed`. Она стирает данные визитки и заливает заново (в одной транзакции, идентификаторы начинаются с 1).

Так поведение предсказуемо: чистый запуск даёт готовую базу, повторный запуск ничего не ломает, а разрушительное действие выполняется только по явной команде. В боевой системе данные менялись бы миграциями или через админку, а seed использовался бы только для dev и демо.

### GraphQL и Apollo Sandbox

- Схема создаётся из TypeScript-классов (code-first), файл схемы вручную не поддерживается.
- Apollo Sandbox включён на `/graphql`. В production Apollo по умолчанию отключает introspection, из-за чего Sandbox не видит схему, поэтому `introspection: true` включён явно.

### Docker

- `docker-compose.yml` описывает PostgreSQL (с проверкой готовности) и приложение. Приложение стартует после того, как база готова.
- `Dockerfile` собирает приложение на `node:24-slim`. При старте контейнер применяет миграции, заполняет пустую базу и запускает сервер.
- Строка подключения берётся из переменной `DATABASE_URL`, порт из `PORT` (по умолчанию 3005). Секреты в репозиторий не попадают: `.env` в `.gitignore`, образец лежит в `.env.example`.
- Порт базы в `docker-compose.yml` опубликован только на `127.0.0.1`, снаружи он недоступен. Пароль берётся из переменной `POSTGRES_PASSWORD`; значение по умолчанию подходит только для локальной разработки.

## Деплой

Проект развёрнут на [Railway](https://railway.com) из ветки `main` этого репозитория:

- **Приложение** собирается по `Dockerfile` из репозитория. При каждом старте оно применяет миграции и заполняет пустую базу (`npm run start:prod`).
- **База данных**: отдельный сервис PostgreSQL в том же проекте. Приложение получает адрес базы через переменную `DATABASE_URL`, которая ссылается на переменную сервиса базы (в репозитории и в коде строки подключения нет).
- **Автодеплой**: любое слияние в `main` запускает новую сборку.
- **HTTPS и публичный адрес** выдаёт платформа. Корневой адрес перенаправляет на `/graphql`.

Чтобы развернуть самостоятельно, достаточно создать проект с PostgreSQL, добавить сервис из репозитория и задать `DATABASE_URL`.

## Безопасность

Что сделано:

- **API только для чтения**: в схеме есть единственный запрос `profile`, мутаций нет. Данные визитки публичные, поэтому авторизация не нужна.
- **Секреты вне кода**: строка подключения хранится в переменной окружения, файл `.env` не входит в репозиторий.
- **База недоступна из интернета**: в Docker Compose порт PostgreSQL открыт только на `127.0.0.1`, а в облаке база работает во внутренней сети проекта, публичный доступ к ней не включён.
- **Доступ GitHub-приложения платформы** ограничен одним репозиторием.

Что осознанно упрощено (для продуктовой системы это следующие шаги):

- Introspection включён, чтобы Apollo Sandbox показывал схему. Для публичных данных визитки это допустимо.
- Нет ограничения частоты запросов и глубины запросов GraphQL. Схема неглубокая и без циклов, что снижает риск.
- Контейнер запускается от root, а в образе остаются dev-зависимости: они нужны `prisma` и `tsx` для миграций и seed при старте.

## Структура проекта

```text
prisma/
  migrations/             миграции БД
  schema.prisma           модели данных
  seed.ts                 логика заполнения БД
  seed-data.ts            данные визитки

src/
  prisma/
    prisma.module.ts
    prisma.service.ts     подключение к БД
  profile/
    experience.model.ts   GraphQL-модели
    profile.model.ts
    project.model.ts
    skill.model.ts
    profile.module.ts
    profile.service.ts    бизнес-логика
    profile.service.spec.ts
  app.controller.ts       перенаправление / на /graphql
  app.module.ts           сборка модулей, настройка GraphQL
  app.resolver.ts         GraphQL API
  main.ts                 запуск приложения

test/
  profile.e2e-spec.ts     тесты GraphQL API

Dockerfile
docker-compose.yml
.env.example
```

Папка `src/generated/prisma` создаётся командой `prisma generate` и в репозиторий не входит.

## Команды

| Команда | Что делает |
|---|---|
| `npm run start:dev` | БД, миграции, seed и запуск в режиме разработки |
| `npm run start:prod` | миграции, seed и запуск собранного приложения |
| `npm run build` | генерация Prisma Client и сборка |
| `npm run db:prepare` | запуск PostgreSQL, миграции и seed |
| `npm run db:seed` | заполнить базу, если она пуста |
| `npm run db:reseed` | стереть данные визитки и залить заново |
| `npm run lint` | линтер |
| `npm run test` | unit-тесты |
| `npm run test:e2e` | e2e-тесты GraphQL API |

## Проверка проекта

```bash
npx tsc --noEmit    # типы
npm run lint        # линтер
npm run build       # сборка
npm run test        # unit-тесты
npm run test:e2e    # e2e-тесты
```

Тесты не требуют базы данных: Prisma в них подменяется заглушкой, поэтому результат не зависит от данных.

**Почему нужен Node 24.** Пакеты NestJS 12 распространяются как ES-модули. Jest 30 загружает их синхронно начиная с Node 24.9 и с флагом `--experimental-vm-modules` (он уже прописан в скриптах `test*`). На более старых версиях Node приложение запускается, но тесты нет.
